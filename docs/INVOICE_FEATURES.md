# Invoice Features

## Recipient Selection

When sending an invoice, you can select specific recipients from the client's contacts and billing email. The send modal displays all available contacts with checkboxes. Primary contacts or billing email contacts are pre-selected by default.

Contacts are sourced from:
- The client's `billing_email` field (if it differs from contact emails)
- All contacts associated with the client (`client_contacts` table)

## Test Email

Click the "Test Email" button on any non-paid/non-cancelled invoice to send a test email to yourself. This:
- Sends the invoice email (with PDF attachment and PayPal link if available) to your logged-in email address
- Does **not** change the invoice status
- Does **not** mark the invoice as sent
- Logs a `test_sent` activity entry

## Invoice Activity History

All invoice actions are logged to the `invoice_activities` table and displayed in a timeline on the invoice detail page.

### Tracked Events

| Type | Trigger |
|------|---------|
| `created` | Invoice is created |
| `updated` | Invoice fields are modified |
| `sent` | Invoice is emailed to client(s) |
| `test_sent` | Test email is sent to admin |
| `viewed` | Client opens the public invoice link |
| `payment_recorded` | A manual payment is recorded |
| `cancelled` | Invoice is cancelled |

### Activity Data

Each activity records:
- `type` - Event type (see table above)
- `description` - Human-readable description
- `user_id` - The admin who performed the action (null for client-triggered events like `viewed`)
- `metadata` - JSON with event-specific data (e.g., recipients list, payment amount)
- `created_at` - Timestamp

## Recurring Invoices

Recurring invoices are generated by `GenerateRecurringInvoicesJob`, which runs daily and processes any client whose `recurring_invoice_day` matches today's day-of-month. If a client has `recurring_invoice_auto_send = true`, the invoice is immediately sent via PayPal + email.

### Auto-Send Safety Rails

Before creating an invoice with auto-send on, the job verifies the client has a deliverable recipient — either `billing_email` or at least one contact with an email. **If neither exists, the invoice is NOT created** and the owner gets a Slack DM. This prevents the historical failure mode where PayPal's `createInvoice` would silently fail (it requires a recipient), leaving the draft stuck and invisible.

If the recipient resolves but the actual PayPal call or email send still throws, the catch block now writes an `auto_send_failed` activity entry on the invoice (visible in the timeline with a red warning icon) and DMs the owner via Slack.

### Owner Notification Channel

Slack DMs route to the user with `role = 'owner'` and their `slack_user_id`, falling back to `config('services.slack.owner_user_id')`. Failures are non-fatal — if Slack itself is down the error is logged and the job continues.

## Retainer Reports on Recurring Invoices

Recurring invoices linked to a `RetainerPeriod` automatically include a retainer report — both as a PDF attachment and as a signed online link in the email body.

### Period Matching

When a recurring invoice is generated, the job finds the most recent `RetainerPeriod` whose `period_end <= invoice.issue_date` for that client and stamps it on `invoices.retainer_period_id`. This matches the common pattern where the May 1 invoice bills for the April retainer.

### What the Report Contains

The Blade view at `resources/views/retainer-reports/show.blade.php` renders:
- Period summary (hours used / budget, usage %, monthly amount)
- Breakdown: human time, meetings, agent-equivalent hours
- **Period activity** (context only — not counted toward hours): GitHub PRs merged + opened, issues closed (via `github_repos.client_id`), Slack message counts split by internal vs. external sender, with per-channel counts, plus Slack first-response and time-to-merge (median/avg and coverage). See [retainer-slack-sla.md](features/retainer-slack-sla.md).
- Detailed time entries for the period
- Client meeting log
- Agent runs and their costs

The "Period activity" section is intentionally separate from the hours math. PR count and Slack volume are signals of *what happened*, not *how many hours were worked*. Folding them into `total_equivalent_hours` would create perverse signal (chatty clients look well-served, quiet clients look neglected). The shortfall hold uses only the hours-based numbers.

### Delivery

- **PDF attached** to `InvoiceSentMail` — filename `Retainer-Report-{Client}-{YYYY-MM}.pdf`
- **Signed URL** included in the email body — 90-day expiry, no auth required, generated via `RetainerReportController::signedUrlFor()`
- Public view route: `/r/retainer-reports/{period}` (with valid signature)
- Public PDF route: `/r/retainer-reports/{period}/pdf` (with valid signature)

## Hours Shortfall Hold

If a retainer period's `total_equivalent_hours` falls below 80% of `hours_included`, the recurring invoice generation job sets `invoices.pending_review = true` and **skips auto-send**, even if the client has `recurring_invoice_auto_send = true`. The owner is Slack-DM'd with:
- This period's hours used vs. budget
- Breakdown across human time, meetings, agent-equivalent hours
- The trailing 3 retainer periods' usage for context

The invoice shows a yellow "Held for review" banner on the show page until you manually send it. Sending an invoice (`InvoiceService::markAsSent()`) clears `pending_review`.

The 80% threshold is intentional — it catches both genuine shortfalls and silent integration failures (e.g., time entries not syncing). A "no data" period and a "low data" period get the same treatment: review before billing.

An `InvoiceActivity` of type `held_for_review` is written with the full snapshot in metadata, so the invoice timeline shows the reason and the historical context.

## Automated Reminders

Invoice payment reminders are scheduled when an invoice is marked as sent and processed by a queued job that runs every minute (`SendInvoiceRemindersJob`, registered in `routes/console.php`).

### Schedule Resolution (precedence)

When an invoice is sent, the reminder schedule is resolved in this order:

1. **Per-client override** (`invoice_reminder_schedules.scope = 'client'`) — if the client has a custom schedule, it wins
2. **Global schedule** (`invoice_reminder_schedules.scope = 'global'`) — applies to every client without an override
3. **Built-in default** — used only if no rows exist in `invoice_reminder_schedules`. Matches the historical hardcoded cadence: `-3, 0, +7, +14, +30` days from the due date.

### Where to Edit

- **Global schedule**: `/invoices/settings` — accessible from the "Reminder Settings" button on the invoices index. Saving here re-materializes pending reminders for every unpaid invoice whose client does **not** have a per-client override.
- **Per-client override**: client detail page → Settings tab → "Invoice Reminder Schedule" card. Saving re-materializes pending reminders for that client's unpaid invoices only.
- **Per-invoice tweaks**: invoice detail page → Reminders card. You can cancel individual pending reminders, edit a reminder's scheduled time, add an ad-hoc reminder, or toggle the "Reminders disabled for this invoice" switch (which cancels all pending reminders and prevents future scheduling for that invoice).

### Schedule Shape

Each schedule row has:
- `offset_days` — integer between `-90` and `+365`. Negative = before due, `0` = on due, positive = after due. The reminder `type` (`before_due` / `on_due` / `overdue`) is derived from the sign of this value.
- `enabled` — per-row toggle; disabled rows are kept in the configuration but skipped when scheduling.

The parent schedule also has its own `enabled` flag — a master switch for the entire scope. If global `enabled = false`, no reminders are scheduled for any client without an override. Same for per-client.

### Data Model

| Table | Purpose |
|-------|---------|
| `invoice_reminder_schedules` | Stores global + per-client schedule configurations (`scope`, `client_id`, `enabled`, `schedule` JSON). |
| `invoice_reminders` | Materialized rows for each scheduled reminder per invoice (`scheduled_at`, `status`, `sent_at`). |
| `invoices.reminders_disabled` | Boolean flag to disable reminders for a single invoice. |

### Re-materialization

Whenever a schedule is saved, the system cancels existing pending reminders on every affected unpaid invoice and recreates them from the new schedule. Sent/cancelled/failed reminders are left as historical records.

Affected invoice scope:
- **Global save** → all unpaid invoices for clients without a per-client override
- **Client save** → all unpaid invoices for that one client
- **Removing a client override** → that client's unpaid invoices fall back to global

## PayPal Integration

### How It Works

PayPal invoices are created lazily — either when the invoice is first sent to a client, or when the client first views the public invoice link. The PayPal invoice is auto-sent (without emailing the recipient) to activate the payment link, which is then embedded in the Zao-sent email and public invoice page.

### Duplicate Invoice Number Handling

PayPal enforces unique invoice numbers per account. If an invoice number already exists in PayPal (from testing, Harvest imports, manual PayPal invoices, etc.), the system handles it as follows:

- **DRAFT duplicates**: Updates the existing PayPal invoice with current local data (amount, line items, recipient), then sends it
- **SENT duplicates with matching amounts**: Links directly (safe — data already matches)
- **SENT duplicates with mismatched amounts**: Cancels the stale PayPal invoice and creates a fresh one with a `-R1` suffix
- Retries up to 5 times with incrementing suffixes (`-R1`, `-R2`, etc.)

### Troubleshooting Artisan Commands

| Command | Description |
|---------|-------------|
| `paypal:diagnose {invoice_id}` | Full diagnostic — tests config, checks PayPal state, retrieves payment link |
| `paypal:check-invoice {invoice_id}` | Fetches current PayPal invoice details and all links |
| `paypal:find-invoice {invoice_id}` | Searches PayPal for invoice by number and links it |
| `paypal:send-invoice {invoice_id} {--no-email}` | Sends/activates a PayPal invoice |

### Fixing a Mislinked PayPal Invoice

If an invoice is linked to the wrong PayPal invoice (wrong amount, wrong recipient), clear the `paypal_invoice_id` field on the invoice record. The next public view or send will trigger fresh PayPal invoice creation with correct data.
